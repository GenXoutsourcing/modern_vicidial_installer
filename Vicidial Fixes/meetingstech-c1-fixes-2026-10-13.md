## 1. vicidial_log lock contention (VDadapt) — FIXED 2026-10-12
- Cause: AST_VDadapt.pl hour-bucket and 30-minute count queries on vicidial_log used the stock `FORCE INDEX (call_date)` (r618, mattf, 2007). 485 ms per query under a table read lock; vicidial_log was 44% of all lock waits; peaks 2-3 s routine, 10-14 s at the :11 and :33 crons.
- Fix: `ALTER TABLE vicidial_log ADD INDEX campai_dt_stat_usr(campaign_id,call_date,status,user)` (covering index, plan shows "Using index"); AST_VDadapt.pl line 83 = `$vicidial_log = 'vicidial_log FORCE INDEX (campai_dt_stat_usr) ';` with line 82 commented. Query 485 ms → 84 ms; vicidial_log disappeared from the contention lists; :11/:33 stalls went from 10-14 s to 2-5 s.
- Also: `--vlog-daily` added to the 00:30 `ADMIN_archive_log_tables.pl --daily --carrier-daily` cron (24 h retention of vicidial_log and vicidial_amd_log; 4.26M → 1.64M rows at start of day).
- Rollback: `/root/premig/AST_VDadapt.pl-BEFORE-20261012-190443` (stock file), `ALTER TABLE vicidial_log DROP INDEX campai_dt_stat_usr`.
- Upgrade note: any VICIdial upgrade overwrites AST_VDadapt.pl and restores FORCE INDEX (call_date); re-apply line 83 or the index is dead weight.
- Residual (2026-10-15): campaign 1023 alone writes 1.1M vicidial_log rows a day; by late afternoon the five per-pass stats scans take ~1 s each even on the covering index and occasionally queue (143 waiters, 4 s max at 17:14). Grows until the 00:30 archive empties the table. Structural answer would be InnoDB for vicidial_log, which VICIdial Group rejects (section 14); left as is.

## 4. Agents "losing connection" / auto-paused / HTTP 500 — FIXED 2026-10-13 (two causes)
- Cause A: ephemeral TCP port exhaustion on agent1-4. Every agent poll opens a new MySQL connection to db1 (~380/s per server); 23,000 TIME_WAIT sockets per server against a 28,000-port range → `mysqli_sql_exception: Cannot assign requested address` → HTTP 500 → stale screen → VDauto_dial auto-pause.
- Fix A: `net.ipv4.ip_local_port_range = 15000 65000` and `net.ipv4.tcp_tw_reuse = 1`, applied live and persisted in `/etc/sysctl.d/90-vicidial-tcp.conf` on agent1-4.
- Cause B (the all-day floor of 20-45 500s per minute per server): PHP 8.1+ mysqli defaults to `MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT`, so VICIdial's by-design duplicate inserts throw (manDiaLlogCaLL vs the dialer's own vicidial_log insert; Matt Florell 2010: "That's normal. You can safely ignore."). Then PHP 8 fataled on `fwrite(false)` because VICIdial writes its own log files into /var/www/html/agc, which the installer left root:root 755.
- Fix B: line 2 of `/var/www/html/agc/dbconnect_mysqli.php` and `/var/www/html/vicidial/dbconnect_mysqli.php` = `mysqli_report(MYSQLI_REPORT_OFF);` plus `chgrp apache /var/www/html/agc; chmod 775 /var/www/html/agc`, on agent1-4, admin, api and the 10-box mt-agent. 500s went to 0 within a minute. Steve decided NOT to add these to the installer script; apply per cluster by hand.
- PHP-FPM pm.max_children 50 → 200 → 400 → **150** (start 30, min_spare 15, max_spare 60). 400 made the MyISAM lock storms worse; 150 bounds database concurrency. **2026-10-21: agent1 raised to 250 (max_spare 80) plus Apache event MPM ThreadsPerChild 64 / MaxRequestWorkers 1024 for the +50-100 agent intake; safe now because live tables are MEMORY and connections are pooled (section 8). applied to agent2-4 at 17:29 the same day; see the change log. HAProxy leastconn with no stickiness is correct.

## 5. MyISAM live_agents freeze storms — FIXED with the VICIdial Group MEMORY recipe, APPLIED 2026-10-13 21:25
- Mechanism: vicidial_live_agents takes 1,000+ statements/s; MyISAM grants one table lock at a time; agi-VDAD_ALL_inbound.agi takes `LOCK TABLES vicidial_live_agents WRITE` on every inbound call and everything queues behind it (113-785 threads in metadata-lock wait for 1-3 s, agent screens freeze, PDROP). Do NOT remove the lock (Matt, 2015).
- Recipe (docs/LOAD_BALANCING.txt, docs/BASE_INSTALL.txt, forum t=40586): `ALTER TABLE vicidial_live_agents MODIFY closer_campaigns VARCHAR(8000) default ''; MODIFY external_ingroups VARCHAR(8000) default ''; MODIFY agent_territories VARCHAR(1000) default ''; ALTER TABLE vicidial_live_agents ENGINE=MEMORY; ALTER TABLE vicidial_manager ENGINE=MEMORY;` and the flush cron `1,5,9,...,57 * * * * AST_flush_DBqueue.pl --seconds=240 --session-flush -q`. Column sizes MUST be 8000/8000/1000 (a c1 user has a 4,923-character closer_campaigns). Verified on the 10-box first (`meetingstech-memory-recipe-10box-verification-2026-10-13.md`: 22-item pass/fail, replica resync procedure, restart behaviour). Result on c1 next morning: lock-wait 1.2% vs 6.0% at 09:32, 4.7% vs 9.6% at 09:37, 6.8% vs 14.6% at 10:01; live_agents gone from the contended-table lists; zero auto-pause storms.
- Addendum 2026-10-14 11:39: vicidial_manager secondary indexes (uniqueid, callerid, serverstat) changed to `USING BTREE`: with the stock HASH indexes ~53% of rows share uniqueid='' in one hash chain and the flush's `DELETE from vicidial_manager` held the table ~8 s every 4 minutes (585 threads queued); with BTREE it completes in well under a second and flush runtime fell from 21-28 s to 13-14 s (5-11 s by 10-15). Rollback = same ALTER with `USING HASH`.
- Caveats: a MySQL restart empties MEMORY tables (agents re-login); after a replica restart run `scripts/resync-orch.sh`. flushmon (`scripts/flushmon.sh`, cron every minute on db1) alerts on manager rows older than 540 s, pending commands older than 30 s, flush runtime over 60 s, capacity over 70%. Rollback: `/root/premig/c1-ROLLBACK-memory-recipe.sql` + crontab backup, with 0 agents.

## 6. vicidial_agent_log lock storm (VDadapt agent-time stats) — FIXED 2026-10-14 13:29
- Cause: all 7 active campaigns have Real-Time Agent Time Stats = CALLS_WAIT_CUST_ACW_PAUSE, so every VDadapt pass runs three full-day aggregates per campaign over vicidial_agent_log (sum pause/wait/talk/dispo, sum wait+talk+dispo, count lead_id>0). No index started with campaign_id, so each was a 346k-row MyISAM scan (~1.1 s): 21 scans ≈ 40 s of table lock per minute. Every agent disposition, READY click and call-arrival write queued behind it (up to 136 waiters, Table_locks_waited +129k/min). Measured impact 11:30-13:29 on 10-14: average after-call time 3-6 s → 19-38 s, agent wait 12-18 s → 24-35 s, PHP-FPM max_children on agent2/3/4, and 14-27% of inbound calls routed to an agent whose screen never took them (closer_log row with the agent's user, no agent_log row, caller hung up in QUEUE). - Fix: `ALTER TABLE vicidial_agent_log ADD INDEX campaign_time (campaign_id, event_time);` (5.5 s, replicated). Plan went from 346k rows to a range of ~80-31k per campaign; VDadapt scan visible 2 of 120 samples instead of ~80; waiters 0; after-call time back to 3.4-3.7 s within one slot; inbound calls without an agent_log row went from 14-27% to 0.06% (the residual is the normal blended race). Nothing updates campaign_id/event_time after insert, so the index costs one key per insert.
- Rollback: `ALTER TABLE vicidial_agent_log DROP INDEX campaign_time;`. Backup `/root/premig/c1-create-vicidial_agent_log-BEFORE-index-20261014-132623.txt`. Alternative without schema change: Real-Time Agent Time Stats = NONE per campaign (loses the realtime report's agent time columns).
- Note for the client: a closer_log row with no agent_log row is a call the agent never got, not a deletion; the nightly archive never touches vicidial_agent_log except by copying it (section 12). An agent_log row can also sit under a different lead_id than the inbound call when the agent transferred or 3-wayed to another lead (the row carries the lead active at disposition).

## 8. Web-tier handshake loss / PHP-FPM pool pile-ups — DIAGNOSED 2026-10-15, proven on the 10-box, APPLIED to c1 agent1-4 2026-10-21
- **APPLIED to c1 agent1-4 on 2026-10-21 14:54-15:03** (Steve approved after a one-host trial on agent1). Result at 15:19: SYN retransmits 12-22 -> 0-1 per 10 s per host, TIME_WAIT 21-24k -> 6.8k, PHP-FPM workers 108-135 -> 65 with zero max_children hits, LB response 500 ms -> 42 ms, db1 new connections 1,700/s -> 565/s (dialers, admin, api still per-request), Threads_connected ~800 with ~133 pooled per host. Zero 500s or mysqli errors. Rollback per host: /root/premig/ROLLBACK-pconn-<ts>.sh. Post-upgrade checklist: re-apply after any VICIdial upgrade (both dbconnect files are overwritten).
- Symptom: all four agent hosts' PHP-FPM pools (150 workers) fill within the same second, several times during the afternoon peaks (10-15: 12:38-13:05, 13:25-13:48, 16:0x, 16:43-16:54, 17:02-17:29). Zero 500s, zero fatals; requests complete, just slowly; manager commands pend 30 s at the worst moments (flushmon alerts).
- Cause: lost TCP handshakes between the web hosts and the DB hosts, not database load. db1 accepts ~2,000 new connections per second (every agent request opens a fresh MySQL connection) and holds ~22,000 TIME_WAIT sockets; during the episodes db1 retransmits 100-180 SYN-ACKs per 20 s, agent1 retransmits 50-160 SYNs per 20 s (1.8% of connects), and each lost handshake packet costs a worker 1-3 s. A connect probe from agent1 shows p90 75-90 ms and up to 1.4 s to db1:3306, the same tail to db1:22 (sshd) and to db2:3306 (another host), while the identical probe from a sip host is flat at 3-9 ms. Everything host-side is clean on both ends: no NIC drops or transmit hangs, softnet 0, conntrack invalid/drop 0 (firewalld's INVALID-drop rules are not firing), no CPU steal, db1 77% idle at 30 MB/s on a 1 Gbps link, listen queues empty, lock waits only 4.3% of 26,000 statements/s. The loss therefore sits on the web hosts' network paths (IONOS) and is amplified by the connect rate.
- Fix proven on the 10-box (mt-agent, 2026-10-15, left in place there): persistent mysqli connections, `p:` prefix on the host in `agc/dbconnect_mysqli.php` line 69 and `vicidial/dbconnect_mysqli.php` line 97 (`"p:".$server_string`, covers the slave path). Same 30-agent load: new DB connections 15,001 → 5,076 per 4 min (the remainder are per-call AGI/daemon connects, none from PHP), 0 errors, latencies equal or better. Risk tests: killing all pooled connections under load → 0 errors, transparent reconnect; MariaDB restart → next requests 200 and agents logged in and dialed; session state (`SET @var`) is NULL on the next request over the same connection (mysqlnd resets the connection on reuse; Com_change_user stays 0 because it uses COM_RESET_CONNECTION). c1 sizing: ~600 pooled connections on db1 (4 × 150 workers) plus admin/api, against max_connections 6,000. Rollout must be one host at a time with the HAProxy backend drained, because the php-fpm restart drops in-flight requests. Not stock: re-apply after upgrades (same as the mysqli_report line). Steve chose to wait and observe (10-15 13:40).
- Also recommended: IONOS ticket for the four web hosts' paths with the retransmit figures.

## 17. Lost vicidial_agent_log rows ("call handled, no agent_log row") — ROOT CAUSE FOUND 2026-10-17, PROVEN on the 10-box, APPLIED to c1 agent1-4 2026-10-19 11:22
- **Symptom (client, Jesse):** every day a few hundred auto-dial calls over 20 s have no agent_log row. In 19 of 20 samples the agent's row at that moment carries the NEXT call's lead_id; 16 of 20 fell in one 7-minute window (17:11-17:18 on 10-16) across 15 agents and 11 dialers. Daily count on c1: 3,558 (10-13), 4,868 (10-14), 210 (10-15), 233 (10-16): the agent_log index removed the bulk, a residual remains and clusters after 16:00.
- **Mechanism (stock vdc_db_query.php, svn r4032):** every action first replaces the browser-supplied agent_log_id with vicidial_live_agents.agent_log_id (line ~2284, "For every process below, lookup the current agent_log_id"). After a dispo in auto-dial the browser sends VDADready with agent_log=NEW_ID. That request (1) sets vicidial_live_agents.status='READY' first (line ~18753), then runs 6-8 more queries (live_agents housekeeping, QueueMetrics lookup, previous-row timer finalisation, user_group lookup) and only then (2) INSERTs the new agent_log row and writes its id to live_agents (lines ~18942-18949). The dialer assigns the next call as soon as it sees READY. If the browser's VDADcheckINCOMING poll catches that call before step (2) commits, the server stamps lead_id/wait_sec/talk_epoch on the PREVIOUS call's row (the id live_agents still holds); updateDISPO then follows the lead_id (it selects agent_log_id <= X and lead_id = L) and lands on the same old row, while the hangup update (talk/uniqueid) lands on the new row. The previous call loses its identity: exactly Jesse's pattern (A = next call's lead, talk 0; B = lead NULL, same uniqueid).
- **Why afternoons, why clusters:** two things widen the window. (a) Queue pressure: after 16:00 agents fall from 185 to 106 with the same contact rate, so the next call lands within 1 s of READY in 39-47% of connects (4-10% in the morning).
