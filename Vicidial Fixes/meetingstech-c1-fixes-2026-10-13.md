Cluster: db1 74.208.140.95 (master), db2 62.151.177.143 + db3 70.35.205.239 (replicas; reports read db2), LB agent-c1 104.219.42.249 (HAProxy leastconn, TLS termination), agent1-4 web (PHP-FPM 8.2.34, Apache mpm_event), admin, api, archive, sip1-30 dialers (Asterisk, 12-core). ## 1. vicidial_log lock contention (VDadapt) — FIXED
- Cause: AST_VDadapt.pl hour-bucket and 30-minute count queries on vicidial_log used the stock `FORCE INDEX (call_date)` (r618, mattf, 2007). 485 ms per query under a table read lock; vicidial_log was 44% of all lock waits; peaks 2-3 s routine, 10-14 s at the :11 and :33 crons.
- Fix: `ALTER TABLE vicidial_log ADD INDEX campai_dt_stat_usr(campaign_id,call_date,status,user)` (covering index, plan shows "Using index"); AST_VDadapt.pl line 83 = `$vicidial_log = 'vicidial_log FORCE INDEX (campai_dt_stat_usr) ';` with line 82 commented. Query 485 ms → 84 ms; vicidial_log disappeared from the contention lists; :11/:33 stalls went from 10-14 s to 2-5 s.
- Also: `--vlog-daily` added to the 00:30 `ADMIN_archive_log_tables.pl --daily --carrier-daily` cron (24 h retention of vicidial_log and vicidial_amd_log; 4.26M → 1.64M rows at start of day).
- Rollback: `/root/premig/AST_VDadapt.pl-BEFORE-20261012-190443` (stock file), `ALTER TABLE vicidial_log DROP INDEX campai_dt_stat_usr`.
- Upgrade note: any VICIdial upgrade overwrites AST_VDadapt.pl and restores FORCE INDEX (call_date); re-apply line 83 or the index is dead weight.

## 3. Phantom calls / balance dialing — FIXED
- Cause: the `servers` table had max_vicidial_trunks=125 and vicidial_balance_active=Y on non-dialers (db1, db2, db3, api, admin, archive, LB, agent1-4). AST_VDauto_dial_FILL.pl on db1 overflowed calls to them whenever the sips hit their trunk cap. No AST_manager_send runs there, so vicidial_manager NEW rows were never processed and vicidial_auto_calls SENT rows sat forever (125 on db2, 31 on api); leads were burned without a call.
- Fix: trunks=0 and balance=N on all 11 non-sip servers; sip1-30 max_vicidial_trunks 125 → 150 → 200 (they were pinned at 125; VDauto_dial logged "LOCAL TRUNK SHORTAGE"); deleted 156 phantom auto_calls rows and 147 stuck manager rows (snapshots in /root/premig).
- Rollback SQL: `/root/premig/nonsip-servers-trunks-REVERT-*.sql`, `/root/premig/sip-servers-trunks*-REVERT-*.sql`.

## 4. Agents "losing connection" / auto-paused / HTTP 500 — FIXED (two causes)
- Cause A: ephemeral TCP port exhaustion on agent1-4. Every agent poll opens a new MySQL connection to db1 (~380/s per server); 23,000 TIME_WAIT sockets per server against a 28,000-port range → `mysqli_sql_exception: Cannot assign requested address` (17,000/hour on one server) → HTTP 500 → stale screen → VDauto_dial auto-pause (`UPDATE vicidial_live_agents SET status='PAUSED', random_id='10' WHERE last_update_time < ...`).
- Fix A: `net.ipv4.ip_local_port_range = 15000 65000` and `net.ipv4.tcp_tw_reuse = 1`, applied live and persisted in `/etc/sysctl.d/90-vicidial-tcp.conf` on agent1-4. Failures dropped to zero the same minute.
- Cause B (the all-day floor of 20-45 500s per minute per server): PHP 8.1+ mysqli defaults to `MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT`, so VICIdial's by-design duplicate inserts throw. The agent action `manDiaLlogCaLL` inserts into vicidial_log and collides with the dialer's own insert for the same uniqueid (Matt Florell, 2010: "That's normal. You can safely ignore."). The request died at the insert, so the follow-up UPDATEs (list_id, MANUAL comment, user_group, alt_dial, and the vicidial_auto_calls uniqueid link) were skipped on every affected manual call. Once that was fixed, PHP 8 then fataled on `fwrite(false)` because VICIdial writes vicidial_mysqli_errors.txt, xfer_log.txt, call_url_log.txt and vicidial_debug.txt into /var/www/html/agc, which the installer left root:root 755 (PHP-FPM runs as apache).
- Fix B: line 2 of `/var/www/html/agc/dbconnect_mysqli.php` and `/var/www/html/vicidial/dbconnect_mysqli.php` = `mysqli_report(MYSQLI_REPORT_OFF);` plus `chgrp apache /var/www/html/agc; chmod 775 /var/www/html/agc`, applied on agent1-4, admin, api, and on the 10-box mt-agent. 500s went to 0 on all servers within a minute. VICIdial Group's own ViciBox still ships PHP 7.4, so upstream never hit this. Steve decided NOT to add these to the modern installer script; apply per cluster by hand when needed.
- PHP-FPM pm.max_children 50 → 200 → 400 → **150** (start 30, min_spare 15, max_spare 60). 400 made the MyISAM lock storms worse (1,600 workers queued on live_agents → 23,000 waits per 5 min, calls stopped reaching agents). 150 bounds database concurrency and lets the FPM socket backlog absorb bursts. The 50 cap was never the cause of the 500s.
- HAProxy leastconn with no stickiness is correct: the agent interface is stateless and carries credentials per request. The LB's 5xx counter equals the sum of the backends' 500s.

## 5. MyISAM live_agents freeze storms — MITIGATED, structural fix scheduled
- Mechanism: vicidial_live_agents takes 1,000+ statements/s (agent polls, per-call AGI scripts, VDauto_dial on 30 dialers); MyISAM grants one table lock at a time; load grows with agents × calls. agi-VDAD_ALL_inbound.agi (line 3132) takes `LOCK TABLES vicidial_live_agents WRITE` on every inbound call; that lock waits behind the whole queue and everything arriving queues behind it: 113-785 threads in "Waiting for table metadata lock" for 1-3 s, agent screens freeze, the PHP pools fill, and call-to-agent assignment waits in the same queue (PDROP, dead calls). Do NOT remove the lock (Matt, 2015: causes wrong or double calls).
- 40% of live_agents statements were `SELECT count(*) FROM vicidial_live_agents where user!='X'` from user_authorization() (agc/functions.php line 220). It exists only for the ViciHost MXAG agent cap (hosted_settings is empty here). A two-line guard was applied and then reverted at Steve's request; data did not show it as causal of anything, but it stays reverted.
- Structural fix, which is VICIdial Group's own documented recipe (docs/LOAD_BALANCING.txt, docs/BASE_INSTALL.txt, forum thread t=40586): `ALTER TABLE vicidial_live_agents MODIFY closer_campaigns VARCHAR(8000) default ''; ALTER TABLE vicidial_live_agents MODIFY external_ingroups VARCHAR(8000) default ''; ALTER TABLE vicidial_live_agents MODIFY agent_territories VARCHAR(1000) default ''; ALTER TABLE vicidial_live_agents ENGINE=MEMORY; ALTER TABLE vicidial_manager ENGINE=MEMORY;` and the flush cron changed to `1,5,9,13,17,21,25,29,33,37,41,45,49,53,57 * * * * /usr/share/astguiclient/AST_flush_DBqueue.pl --seconds=240 --session-flush -q` (its 22 unconditional OPTIMIZE TABLE statements are instant on MEMORY tables and keep the 41 cid_channels_recent_* tables small). Tested on the 10-box including a MariaDB restart (replica reconnects within 60 s; slave_skip_errors 1032,1062,1690 already set on both clusters). **APPLIED ON c1 2026-10-13 21:25** (Steve approved after the 10-box verification; heap raised to 2G on db1/db2/db3 first; 4-min flush cron + flushmon on db1). Verification report: `meetingstech-memory-recipe-10box-verification-2026-10-13.md`. Column sizes MUST be 8000/8000/1000 per the docs bundled with this build; a c1 user has a 4,923-character closer_campaigns value, so the 200/200/45 sizes first used on the 10-box would have truncated in-group membership (corrected on the 10-box 18:09). Rollback: `ENGINE=MyISAM` on both tables plus the crontab backup. Caveat: a MySQL restart empties MEMORY tables, so all agents must re-login. **Addendum 2026-10-14 11:39:** the three secondary indexes of vicidial_manager (uniqueid, callerid, serverstat) were changed to `USING BTREE` on c1 (replicated to db2/db3): with the stock HASH indexes, ~53% of rows share uniqueid='' in one hash chain and the flush's `DELETE from vicidial_manager` held the table ~8 s every 4 minutes (585 threads queued); with BTREE it completes in well under a second and flush runtime fell from 21-28 s to 13-14 s. Deviation from the published recipe, index type only; rollback = same ALTER with `USING HASH`; re-apply after any upgrade that rebuilds the table.

## 6. Dialing pipeline and dead calls — DIAGNOSED (client-side levers)
- PDROP means the answered party hung up during AMD, before the routing AGI (FastAGI_log.pl line 2143). It is not "no agents available".
- AMDY vendor round trip (ws://api.amdy.io:2700): 1.0 s early morning, 1.2-1.7 s from 10:00 onward; NOTSURE verdicts jumped from 5 to 400 per 10 minutes at 10:00. The client hand-set the dial level from 1 to 20 (RATIO mode, VDadapt does not set it). Result: agent calls ending within 5 s rose from 5% to 12%, PDROP from 1% to 2.7%.
- Decision-to-INVITE delay grew from 1.6 s to 5 s average at dial level 20: AST_manager_send drains about 7 originates per second per dialer (one forked child per originate); Asterisk to carrier is a constant 0.55 s. Levers are a lower dial level or more dialers; trunk caps do not change it.
- The real-time report's "3-WAY" is a heuristic: more than one agent INCALL on the same lead_id, and it shows the newest call's timer for all of them. Four agents hand-dialling the same lead (list 998 "Default Manual list") looked like one 3-way.
- The client loads leads with DISABLE KEYS / ENABLE KEYS (mysqldump style), which rebuilds every vicidial_list index per batch: 35-101 s agent freezes each time. Use plain inserts, the lead loader, or off-hours.
- call_log at 4.7M rows is 38 hours of per-channel-leg rows (1.7 per dial), trimmed nightly by `--daily` to 24 hours. Normal.
- vicidial_agent_latency_log is already enabled; agent-side browser round trip averages 250-310 ms, over 1 s only 0.1% of polls. Agent networks were never the problem.
- vicidial_auto_calls is MEMORY in the stock schema (all indexes HASH, so time-range filters full-scan a ~2,000-row table; measured as negligible).
